## Findings — Round 1 (initial sweep)

### ✅ P0 — recursion when PATH wrapper points at a different cmdguard
**Status**: **FIXED** in commit `1ba4f48` (sentinel detection) +
`dbc162f` (BinDir helper, --bin-dir flag, init guide cleanup).

Repro before fix: with `CMDGUARD_CONFIG_DIR` pointing to a non-default
path but `PATH` still containing `~/.cmdguard/bin/`,
`cmdguard rm <file>` hung for seconds, executed
`/Users/haolin/.cmdguard/bin/rm` (the wrapper), wrapper called
`/Users/haolin/Bin/cmdguard rm`, which looped back into cmdguard.

Root cause: `findRealCommand` skipped ONLY paths under
`config.ConfigDir()/bin`. When the runtime overrode `CONFIG_DIR` to a
sandbox dir, the *production* `~/.cmdguard/bin/` wrapper was not
skipped. `os.SameFile(self, target)` did not save us either because
the wrapper is a shell script, not the cmdguard binary.

Fix: every wrapper script generated by `cmdguard init` now embeds a
`# cmdguard:wrapper:v1` sentinel line. `findRealCommand` reads the
first 256 bytes of each PATH candidate that looks like a shell script
and skips any file containing the `# cmdguard:wrapper:` prefix.

Verification: rebuilt audit binary, re-ran the original repro, got a
single Warning + clean exit + file removed. Was: 4+ recursion
iterations + watchdog SIGTERM + file untouched.

Migration note: existing `~/.cmdguard/bin/` wrappers from earlier
installs do NOT carry the sentinel. Three options for upgraders:
1. `cmdguard init --force` (rewrites wrappers cleanly)
2. Manually add `# cmdguard:wrapper:v1` as line 2 of each wrapper
3. Leave alone — only matters if PATH carries another cmdguard install

The author's local install was patched manually with option 2 during
the sweep.

### ✅ P1 — `init` integration guide referenced non-existent `cmdguard env-path`
**Status**: **FIXED** in commit `dbc162f`.

The guide now suggests `export PATH="$(cmdguard config --bin-dir):$PATH"`
which uses the new --bin-dir flag added in the same commit.
